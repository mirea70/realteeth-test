## 1. 프로젝트 아키텍처 (Architecture)
```text
┌── domain
├── application
├── util
├── adapter-out-persistence
├── adapter-out-mq
├── adapter-out-worker
├── adapter-in-api       // 클라이언트로 요청 수신
├── adapter-batch        // 스케줄러 담당
└── adapter-in-worker    // Worker와 통신
```

구현해야하는 시스템은 크게 요청 수락을 담당하는 로직과, 외부 Mock Worker 호출을 담당하는 로직으로 나눌 수 있습니다. 두 로직을 함께 둔다면, 트래픽이 증가했을 때, 외부 Mock Worker 작업이 오래걸릴 수도 있는 특성 상 병목이 걸려, 클라이언트에 응답을 반환하는데 지연이 발생해 사용자에게 불편함을 초래할 수 있습니다.

이에 따라 두 로직을 별도의 서버 애플리케이션으로 분리하여, 추후 트래픽에 대응하기 위해 시스템을 분산 시 용이하도록 하였습니다. 이를 구현하기 위해 멀티모듈 구조를 활용했습니다.

또한 설계한 시스템은 DB, MessageQueue, Mock Worker 등 여러 외부 시스템을 사용하고 있습니다. 특히 Mock Worker는 과제 기간 동안 변경되지 않는다고 안내 받았지만, 실제 운영 환경에서는 **충분히 지속적으로 변경이 가능하다는 특성**을 가진 것으로 이해했습니다. 뿐만 아니라 불확실성이 존재하는 환경이라 가정한다면, **연동할 외부 시스템은 얼마든지 변경될 수 있다는 점을 고려**해 헥사고날 아키텍처를 적용하여 **외부 기술이 변경되더라도, 도메인의 핵심 규칙이 보존**될 수 있도록 설계하였습니다.

애플리케이션은 앞단에서 클라이언트로 요청을 수신하는 API 애플리케이션, 이벤트 발행 및 복구 등 스케줄러를 담당하는 Batch 애플리케이션, 발행된 이벤트를 수신하여 Worker와 통신하게되는 Worker 애플리케이션 총 3개로 구성하였습니다.

</br>

### 모듈 구성 (Multi-Module)
- `modules/domain`: 업무 핵심 로직 및 엔티티 (`ImageJob`, `OutboxEvent`) 정의
- `modules/application`: 비즈니스 UseCase 인터페이스 및 서비스 레이어 구현
- `modules/adapter-in-api`: REST API 진입점 (`RestController`)
- `modules/adapter-out-persistence`: JPA 기반 데이터베이스 접근 영속성 어댑터
- `modules/adapter-out-worker`: 외부 이미지 처리 Worker와의 통신 어댑터 (Mock 연동)
- `modules/adapter-batch`: 아웃박스 이벤트 발행 및 장애 복구를 위한 스케줄러

## 2. 실행 방법 (How to Run)

### 2.1 사전 요구사항
- Java 21
- Docker & Docker Compose

### 2.2 인프라 실행
```bash
docker-compose up -d
```
> MySQL(3306)과 RabbitMQ(5672)가 실행됩니다. `init.sql`에 의해 초기 테이블이 생성됩니다.

### 2.3 어플리케이션 빌드 및 실행
```bash
./gradlew clean build
./gradlew :modules:adapter-in-api:bootRun
```

## 4. 설계 상세

### 4.1 채번 전략
- 추후 샤딩을 적용하는 등 인프라 변경 시, DB_AutoIncrement를 사용할 경우 중복 PK 값이 저장될 수 있으므로, Snowflake 방식을 사용해, DB 다중화가 되더라도 전역 유니크를 보장할 수 있도록 하였습니다.
- 알고리즘 수행 과정에서 nodeId 충돌이 발생할 수 있지만, 확률이 현저히 적으며 nodeId를 할당하는 중앙 시스템을 추가해 이를 사용하면 로직 상 큰 변경 없이 유일성 보장이 가능하다는 점을 고려하였습니다.

</br>

### 4.2 외부 작업 위임 처리 전략
외부 Mock Worker에 의해 수행되는 이미지 처리 작업은 오래 걸리는 작업이며, 외부 시스템 상태에 따라 응답 지연이나 실패가 발생할 가능성이 존재합니다. 따라서  API 서버가 클라이언트 요청을 받은 뒤 외부 Worker를 **동기적으로 호출하는 구조**는 다음과 같은 문제가 예상되었습니다.

- 외부 서비스 지연으로 인해 API 응답 시간이 길어짐
- 동시에 많은 요청이 들어올 경우 API 서버의 스레드가 장시간 점유됨
- 외부 시스템 장애가 API 서버 안정성에 직접적인 영향을 미침

이 문제를 해결하기 위해 요청 수락 로직과 실제 작업 위임 로직을 분리하여 비동기로 처리되는 구조로 설계하기로 했습니다.

</br>

#### 4.2.1 메시지 브로커 사용 계기
비동기 처리 방식으로는 크게 세가지 대안을 고려하였습니다.

##### 멀티 스레드

Spring의 **@Async** 또는 **Executor** 기반 멀티 스레드를 통해 작업을 비동기로 처리할 수 있을 것입니다. 그러나 이러한 방식은 다음과 같은 문제가 예상되었습니다.

- 애플리케이션 프로세스 내부 메모리에 의존하기 때문에 **서버가 재시작되거나 장애가 발생할 경우 진행 중인 작업이 유실**될 가능성이 있습니다.
- API 서버와 Worker에 위임하는 역할이 동일 프로세스에 존재하게 되어 **리소스 경쟁 및 확장성 문제**가 발생할 수 있습니다.

##### DB Polling

작업 정보를 DB에 저장하고 별도의 Worker가 주기적으로 polling하여 처리하는 방식도 고려할 수 있을 것입니다. 하지만 이 방식은 마찬가지로 다음과 같은 단점이 예상되었습니다.

- 일정 주기로 DB를 조회해야 하므로 **불필요한 polling 비용** 발생
- 작업 대기열 관리 및 재시도 로직을 직접 구현해야 함
- 대기 작업이 많아질 경우 **DB 부하** 증가

##### 메시지 브로커 기반 작업 큐

위 방식들과 비교했을 때 메시지 브로커는 다음의 유리함을 갖고 있습니다.

- 서버가 재시작되거나 장애가 발생하더라도 **작업의 유실될 것을 걱정하지 않아도 됩니다**.
- 재시도 처리가 제공되는 시스템을 사용한다면 **직접 구현하지 않고 주요 로직에 집중**할 수 있습니다.
- API 애플리케이션과 분리해 작업 위임 로직을 별도 애플리케이션이나 서버로서 **독립적으로 확장**이 가능합니다.

이에 따라 메시지 브로커 기반 작업 큐 방식이 외부 시스템 호출을 **안정적으로 위임**하고 **확장성을 확보**하는 데 더 적합하다고 판단하여 사용하기로 결정했습니다.

</br>

#### 4.2.2 RabbitMQ 선택 이유
메시지 브로커 후보로 RabbitMQ, Redis Streams, Kafka를 고려해보았습니다.

##### Kafka

Kafka는 대규모 이벤트 스트리밍과 데이터 파이프라인 처리에 강점을 가지며, 로그 기반 저장과, 높은 처리량을 제공하는 장점이 있습니다. 그러나 이러한 특성은 이벤트 스트림을 장기간 보관하고 다양한 소비자가 이를 재처리하게 될 수 있는 환경에서 더 큰 가치를 가지며, 본 시스템처럼 작업을 한 번 소비하여 외부 Worker에 위임하는 문제에서는 상대적으로 **시스템 모델과 운영 복잡도가 불필요하게 커질 수 있다**고 생각되었습니다.

##### Redis Streams

Redis Streams 역시 Consumer Group을 통해 작업 큐와 유사한 구조를 구현할 수 있고 기존 사용 중이던 Redis 인프라와 통합하기 쉽다는 장점이 있지만, 메시지를 소비해도 로그에 계속 남기 때문에 이러한 **pending 메시지 관리와 reclaim 전략 등을 별도로 설계해야 한다는 부담**이 존재했습니다. 

##### RabbitMQ

반면 RabbitMQ는 메시지를 소비하고나면 이를 유지하지 않고 제거되는데, 본 시스템에서는 Worker로 작업 위임에 성공했다면 DB에 작업 정보는 저장해놓지만, 더이상 **메시지는 유지할 필요가 없으므로 적합**하다고 느꼈습니다. 또한 Consumer 장애 시, **메시지 재전송 기능을 제공**하여 추가적인 처리가 필요하지 않다는 장점도 있어 RabbitMQ를 메시지 브로커로 선택하였습니다.

</br>

#### 4.2.3 요청 수행 과정 도식화
지금까지 결정한 내용을 토대로 API 서버에서 이미지 처리 요청의 수행을 도식화 해보겠습니다.

```text
Client
   ↓
API Application
   ↓
DB (Job 저장 + 위임 작업 시작 메세지 발행) // API 애플리케이션 응답
   ↓
RabbitMQ
   ↓
Worker Application // Worker 위임 작업 시작
   ↓
Mock Worker // 이미지 처리 요청
   ↓
Worker Application
	 ↓
DB (Job 진행중으로 상태 전이, RabbitMQ에 작업 진행 추적 메시지 발행, RabbitMQ에 위임 작업 시작 메시지 ACK)
	 ↓
RabbitMQ
	 ↓
Worker Application // Mock Worker의 작업 진행 추적
	 ↓
Mock Worker
   ↓
이미지 처리 성공/실패
	 ↓
DB (상태 갱신, RabbitMQ에 작업 진행 추적 메시지 ACK)
```

</br>

#### 4.2.4 메시지 발행의 유실에 대한 고려
클라이언트가 이미지 처리 요청을 보내면 API 애플리케이션은 먼저 작업(Job)을 생성하고 DB에 저장합니다. 그런데 만약 **작업 정보는 DB에 저장되었지만 메시지 발행에 실패**하면, 시스템에는 처리되어야 할 작업이 존재하지만 Worker는 이를 알 수 없게 됩니다. **반대로 메시지는 발행되었지만 DB 반영이 실패하는 경우**에도 **시스템 정합성이 깨질 수 있습니다**. 이미 위임된 작업을 추적하기 위한 메시지 발행 시에도 마찬가지입니다.

이를 방지하기 위해 Outbox 패턴을 적용하여 다음 두 작업을 **하나의 트랜잭션으로 처리**하였습니다.

- Job 상태 변경(저장/전이)
- Outbox Event(메시지 발행) 저장

그리고 별도의 **Outbox Publisher**가 Outbox 테이블을 조회해 RabbitMQ에 메시지를 발행하고, 발행이 성공하면 해당 Outbox Event는 이후 **추적이나 장애 분석**이 용이하도록 삭제가 아닌, PUBLISHED(**처리 완료**) 상태로 변경되도록 하였습니다.

</br>

#### 4.2.5 작업의 상태 전이 모델 정의
```text
[Client Request]
ACCEPTED
  ↓
[Outbox 저장 완료]
PUBLISH_PENDING
  ↓
[Outbox Publisher가 MQ 발행 성공]
PUBLISHED
  ↓
[Worker가 상태 선점 성공]
DISPATCHING
  ↓
[Mock Worker 위임 성공, Mock Worker의 작업 진행 추적 중]
PROCESSING
  ├─→ [외부 처리 성공] SUCCEEDED
  └─→ [외부 처리 실패] FAILED
```

Mock Worker에 외부 이미지를 요청하는 일은 비용이 크고, 중요한 작업이므로 현재 상황을 보다 정밀하게 추적할 수 있도록 작업의 상태를 아래와 같이 세분화하여 정의하였습니다.

1. **ACCEPTED**
    - 클라이언트 요청을 수락했고, **Job 자체가 생성된 상태**
    - DB에 Job 데이터 생성 완료
2. **PUBLISH_PENDING**
    - 메시지 브로커로 전달해야하는 **이벤트가 DB에 기록된 상태**
    - DB에 Outbox Event 데이터 저장 완료
    - 아직 RabbitMQ에 메시지 발행 전
    - Outbox Publisher는 이 상태의 작업들을 조회하여 메시지 브로커에 메시지를 발행합니다.
3. **PUBLISHED**
    - RabbitMQ로 작업 **메시지 발행이 완료된 상태**
    - API 애플리케이션의 책임은 끝났고, Worker 애플리케이션이 메시지를 수신해 처리하기 전입니다.
    - RabbitMQ는 이 단계에서 Worker 애플리케이션이 메시지를 정상적으로 수신해 Consume 완료할 때까지 재시도 등의 처리를 하게 됩니다.
4. **DISPATCHING**
    - Worker 애플리케이션이 메시지를 수신했으며, 이 Job을 선점하여 **외부 Mock Worker 호출을 시도하고 있는 상태**입니다.
    - 아직 RabbitMQ에 ACK는 보내지 않습니다.
    - 병렬 소비 처리를 하거나, 여러 Consumer가 동시에 같은 Job에 대해 Mock Worker 호출 시도하는 것을 막는 역할도 함께하게 됩니다.
    - 이 단계를 통해 외부 Mock Worker로의 위임 성공 여부를 명확히 구분 가능합니다.
5. **PROCESSING**
    - 외부 Mock Worker에 작업 위임에 성공한 상태입니다.
    - RabbitMQ에 작업 위임 시도 메시지 소비에 대한 ACK를 보낸 상태입니다.
    - 해당 시스템이 실제로 처리 중이며, Worker 애플리케이션이 외부 시스템 처리의 성공/실패 여부를 기다리고 있습니다.
    - RabbitMQ에 Mock Worker의 작업 진행을 추적하는 메시지를 발행하기 위한 Outbox Event를 DB에 저장 완료 상태
    - Outbox Publisher는 해당 이벤트를 조회하여 메시지 브로커에 메시지를 발행합니다.
    - Worker 애플리케이션에서 작업 진행 추적 책임을 가진 컨슈머가 이 메시지를 수신해, Mock Worker의 진행을 추적하고, 성공/실패 여부를 확인합니다.
    - 컨슈머는 Mock Worker가 아직 이미지 처리를 진행 중이면, 다음 Poll 작업을 예약(메시지를 발행 Outbox Event 저장)하고 메시지 브로커에 ACK를 보냅니다.
    - 다음 Poll 작업을 예약할 때는, 바로 조회할 경우 아직 작업이 진행 중일 가능성이 높으므로, 불필요한 상태 조회 반복을 최소화하기 위해 **40초의 간격을 두고 예약을 수행**하도록 하였습니다.
    - 외부 Mock Worker가 이미지 처리 작업을 성공/실패할 때까지 이를 반복합니다.
6. **SUCCEEDED**
    - 작업의 상태가 DB에 SUCCEEDED로 반영
    - 뒤늦게 상태 전이를 시도 하는 것은 전이 로직에서 차단됩니다.
    - RabbitMQ에 작업 진행 추적 메시지 소비에 대한 ACK를 보낸 상태입니다.
7. **FAILED**
    - 작업의 상태가 DB에 FAILED로 반영
    - 뒤늦게 상태 전이를 시도 하는 것은 전이 로직에서 차단됩니다.
    - RabbitMQ에 작업 진행 추적 메시지 소비에 대한 ACK를 보낸 상태입니다.

</br>

#### 4.2.6 데이터 정합성이 깨질 수 있는 지점
본 시스템은 메시지 브로커, DB, 외부 Mock Worker가 함께 동작하는 분산 구조이므로, 특정 상태 전이 구간에서 정합성 문제가 발생할 수 있습니다. 또한 상태 전이 과정에서 지연/실패 등이 발생할 수 있습니다. 이러한 위험 요인과, 그에 대한 대응 전략을 아래와 같이 정리하였습니다.

</br>

##### 1. Job 저장 후 Mock Workcer 호출 시도 메시지 발행 전후

클라이언트 요청을 받아 Job을 생성한 뒤 Mock Worker 호출을 시도하는 메시지를 발행해야 합니다.

이때 Job만 저장되고 메시지가 발행되지 않으면, DB에는 Job이 존재하지만 Worker는 해당 작업을 추적은 할 수 없게 됩니다.

이를 방지하기 위해 **Job 저장과 메시지 발행 Outbox Event 저장을 동일 트랜잭션으로 처리**하였습니다.

이후 Outbox Publisher가 미발행 이벤트를 기준으로 RabbitMQ에 Mock Workcer 호출 시도 메시지를 발행합니다. 이를 통해 **Job이 ACCEPT 상태로 DB**에 저장되어 있다면 해당 작업은 Mock Worker 호출 메시지 발행을 보장할 수 있도록 하였습니다.

</br>

##### 2. 외부 Mock Worker 호출 성공 후 `PROCESSING` 저장 전

```
PUBLISHED
  ↓
DISPATCHING
  ↓
Mock Worker 호출 성공
  ↓
시스템 장애 발생
  ↓
~~PROCESSING 저장 + Poll용 Outbox Event 저장~~
```

이때 Mock Worker 호출은 성공했지만, `PROCESSING` 상태와 `workerJobId`, 그리고 Poll용 Outbox Event 저장 전에 Worker 애플리케이션이 중단되면

- 외부 Mock Worker에는 실제 작업이 생성됨
- 내부 DB에는 여전히 `DISPATCHING` 상태만 남음
- 후속 Poll 메시지도 생성되지 않음

즉 **외부 작업은 시작되었지만 내부 시스템은 그 작업을 추적할 수 없는 상태**가 될 수 있습니다.

이 구간은 외부 HTTP 호출과 내부 DB 저장을 하나의 원자적 연산으로 묶을 수 없기 때문에, 외부 환경을 명확히 상정할 수 없는 현재 조건에서는 완전히 제거하기 어렵습니다.

이를 완화하기 위해, 메시지 브로커에 수신완료 **ACK를** PROCESSING 상태 전이 완료와 다음 Poller 예약을 위한 Outbox Event를 DB에 **반영한 후에 하도록 처리**하였습니다. 이렇게 되면 시스템 장애가 발생하여 메시지 브로커와 Consumer의 연결이 끊겨 **메시지 브로커가 재발행 처리를 수행**하게 되므로 작업 추적이 이어서 가능하게 됩니다.

</br>

##### 3. 작업 진행 추적 Consumer가 외부 상태를 조회했지만, 다음 Poll 예약 또는 최종 상태 저장 전

```jsx
Poll 메시지 수신
  ↓
Mock Worker 상태 조회
  ↓
외부 상태 = PROCESSING / SUCCEEDED / FAILED 확인
	↓
시스템 장애
  ↓
~~다음 Poll용 Outbox Event 저장 OR DB 최종 상태 반영~~
```

외부 상태의 결과를 확인했지만, 다음 Poll 이벤트 저장 OR 최종 상태 DB 반영 전에 시스템 장애가 발생하면 **상태 추적이 중간에 끊기거나**, 실제로 **이미지 처리는 완료되었지만, 내부 시스템 DB에는 반영이 안될 수 있습니다**.

해당 문제도  메시지 브로커에 수신완료 **ACK를 다음 Poll용 Outbox Event 저장 Or 최종 상태 DB에 반영 후 보낸다**면, **메시지 브로커의 Redeilvery 기능**이 작동되어 **작업** **상태 추적을 이어**가거나, 작업 상태의 **정합성을 동기화**시킬 수 있습니다.

</br>

##### 4. 메시지 브로커와 Consumer 연결이 끊기지 않았지만, 소비를 끝내지 못한채 멈춰 있는 상황

RabbitMQ의 redelivery는 주로 connection 종료나 consumer 중단과 같은 명확한 장애를 전제로 동작합니다. 따라서 consumer thread가 hang 상태에 빠지거나, 외부 호출이 비정상적으로 장시간 지연되거나, ACK 이후 잘못된 상태로 남는 경우까지 모두 해결할 수는 없습니다. 이러한 이유로 `DISPATCHING` 및 `PROCESSING` 상태의 **장기 체류를 별도로 감지**하여, 메시지 브로커 기반 복구를 보완하는 안전망으로 활용하도록 하였습니다. 

**작업 상태 복구 전략 (DISPATCHING)**

- **DISPATCHING** 상태로 장기 체류하고있는 작업들을 DB Polling 방식으로 감지(**1분**)하여, 메시지 브로커에 메시지를 재발행할 수 있도록 작업 상태를 **PUBLISH_PENDING**로 변경합니다. 이 때 **장기 체류 시간에 대한 정의는 2분**으로 채택하였습니다.
- 이 때, **무제한 재시도를 방지**하기 위해**, 재시도 횟수**를 카운트하고 **5회를 초과**할 경우 작업 상태를 **FAILED** 상태로 변경하고, 에러 메시지와 마지막 작업 상태를 함께 저장하여 운영 중 확인할 수 있도록 처리하였습니다.
- 이 때, 작업 유실을 막기위해 재시도할 경우 결국 **Mock Worker로의 작업 위임이 중복해서 발생**하게되는 한계가 존재합니다.

**작업 상태 복구 전략 (PROCESSING)**

**PROCESSING** 상태로 장기 체류하고있는 작업들을 DB Polling 방식으로 감지(**3분**)하여 Mock Worker 상태를 직접 재조회합니다. 이 때 **장기 체류 시간에 대한 정의는 5분**으로 채택하였습니다. 그리고 결과에 따라 아래의 분기로 처리하였습니다.

- 외부 상태가 여전히 `PROCESSING`
    - 다음 Poll 이벤트 재생성
    - `poll_attempt_count` 증가
    - **무제한 재시도를 방지**하기 위해**, 재시도 횟수**를 카운트하고 **5회를 초과**할 경우 작업 상태를 **FAILED** 상태로 변경하고, 실패 정보 저장
- 외부 상태가 `SUCCEEDED`
    - `PROCESSING -> SUCCEEDED`
    - 결과 저장
- 외부 상태가 `FAILED`
    - `PROCESSING -> FAILED`
    - 실패 정보 저장

</br>

### 4.3 서버 재시작 시 동작
본 시스템은 외부 Mock Worker와 비동기 메시징(RabbitMQ)을 통해 작업을 수행하는 구조이므로, Worker 애플리케이션 또는 API 애플리케이션이 재시작되는 상황에서도 작업 정합성이 유지될 수 있도록 설계하였다. 서버 재시작 시 동작은 크게 **메시지 발행 복구**, **메시지 재전달 처리**, **장기 체류 상태 복구** 세 단계로 설명할 수 있습니다.

#### 1. Outbox 기반 메시지 발행 복구

본 시스템은 Job 상태 변경과 메시지 발행을 동일 트랜잭션으로 처리하기 위해 Outbox 패턴을 사용하고 있습니다.

따라서 서버가 다음과 같은 상황에서 중단되더라도 메시지 유실은 발생하지 않습니다.

- Job 생성 후 Mock Worker 이미지 처리 호출 시도 메시지 발행 전에 서버 중단
- Poll 이벤트 생성 후 Mock Worker 작업 추적 메시지 발행 전에 서버 중단

이 경우 Outbox 테이블에는 아직 발행되지 않은 이벤트가 남아 있게 됩니다.

서버 재시작 시 **Outbox Publisher의 로직을 수행**시켜 **미발행 이벤트를 다시 읽어 RabbitMQ로 발행**하므로, 메시지 발행이 누락되지 않도록 하였습니다.

즉, **DB 상태와 메시지 발행 사이의 정합성은 Outbox 패턴을 활용해 복구됩니다.**

</br>

#### 2. RabbitMQ 메시지 재전달 처리

Worker 애플리케이션은 메시지를 처리한 뒤 바로 ACK를 보내지 않고, **다음 상태 전이와 후속 작업 예약이 완료된 뒤 ACK를 전송**하도록 설계하였습니다.

예를 들어 Dispatch 단계에서는 다음 순서로 처리됩니다.

1. `PUBLISHED → DISPATCHING` 상태 전이
2. Mock Worker 작업 요청
3. `DISPATCHING → PROCESSING` 상태 전이
4. Poll 이벤트 저장
5. **ACK 전송**

만약 위 과정 중 Worker 애플리케이션이 중단되면 RabbitMQ는 해당 메시지를 ACK 받지 못한 상태로 인식합니다.

이 경우 Worker 재시작 후 동일 메시지는 RabbitMQ에 의해 다시 전달됩니다.

따라서 다음과 같은 상황에서도 작업 처리가 이어질 수 있습니다.

- Mock Worker 호출 직후 서버 중단
- Mock Worker 작업 상태 조회 후 다음 Poll 예약 전에 서버 중단
- 상태 저장 직전 서버 중단

이러한 경우 메시지는 RabbitMQ에 의해 재전달되며, Consumer는 Job 상태를 기반으로 **멱등하게 재처리합니다**.

</br>

#### 3. 장기 체류 상태 복구

RabbitMQ의 메시지 재전달은 주로 **Consumer connection 종료나 프로세스 중단** 상황에서 동작합니다.

따라서 다음과 같은 상황에서는 메시지 재전달만으로 복구가 어려울 수 있습니다.

- Consumer thread hang
- 외부 API 호출 장시간 지연
- 로직 버그로 Poll 이벤트 생성 누락
- ACK 이후 상태 추적 흐름 중단

이 때 위에서 기술한 **작업 상태 복구 전략**의 로직을 시스템 재시작시 즉시 호출하여 **`DISPATCHING`** / **`PROCESSING`** / **`PUBLISHED`** 으로 장기 체류 상태의 작업들에 대한 복구 작업을 실행하도록 처리하였습니다.

</br>

### 4.4 동시성 문제에 대한 고려
#### 1. 동일 Job에 대한 Dispatch 메시지 중복 소비

RabbitMQ의 메시지 전달 보장 모델은 **at-least-once** 이므로, Consumer가 메시지를 처리한 뒤 ACK를 보내기 전에 장애가 발생하면 동일 메시지가 다시 전달될 수 있습니다. 또한 여러 Consumer가 동시에 동일 Job을 처리하려고 시도할 수 있습니다.

이 상태에서 단순히 Job 상태를 조회한 뒤 외부 Mock Worker를 호출하면, 여러 Consumer가 동시에 “아직 처리 가능하다”고 판단하여 외부 작업을 중복 실행할 수 있습니다.

이를 방지하기 위해 본 시스템은 `PUBLISHED -> DISPATCHING` 상태 전이를 **조건부 update**로 처리하였습니다.

즉, 상태 선점에 성공한 Consumer만 외부 Mock Worker 호출을 수행하도록 하여, 동일 Job에 대한 병렬 Dispatch 실행을 차단하였습니다.

</br>

#### 2. 동일 Job에 대한 Poll 메시지 중복 소비

Poll 단계 역시 RabbitMQ 메시지를 기반으로 동작하므로, 동일 Poll 메시지가 재전달되거나 여러 Consumer가 거의 동시에 Poll 로직을 수행할 수 있습니다.

예를 들어 다음과 같은 상황이 가능합니다.

- Poll 메시지 처리 중 ACK 전에 장애 발생
- Poll 복구 스케줄러가 별도로 다음 Poll을 다시 예약
- 중복 Poll 이벤트가 동시에 처리됨

이 경우 여러 Consumer가 같은 Job의 외부 상태를 거의 동시에 조회하고, 동시에 다음 Poll을 예약하거나 최종 상태를 반영하려고 시도할 수 있습니다.

이를 방지하기 위해 Poll Consumer 역시 현재 Job 상태를 기준으로 동작하며,

- 이미 terminal state(`SUCCEEDED`, `FAILED`)인 경우 추가 처리하지 않고 종료
- 상태 전이는 항상 **현재 상태를 조건으로 하는 방식**으로 수행
- 다음 Poll 예약 역시 중복 저장 가능성을 고려하여 멱등적으로 처리

하도록 설계하였습니다.

즉 Poll 단계에서도 **상태 기반 멱등성 + 조건부 update**가 필요합니다.

</br>

#### 3. Outbox Publisher의 중복 발행

Publisher가 장애 후 재시작되거나 여러 인스턴스가 동시에 동작하면 동일 Outbox Event를 중복 발행할 수 있습니다.

이를 방지하기 위해 Outbox 상태를 조건부로 갱신하여 발행 대상 선점 로직을 두었습니다.

</br>

#### 4. 상태 복구 스케줄러와 Worker Consumer 간 충돌

`DISPATCHING` 또는 `PROCESSING` 장기 체류 복구 로직은 별도 스케줄러로 동작합니다.

이때 실제 Worker Consumer가 거의 동시에 같은 Job 상태를 갱신하고 있을 수 있습니다.

예를 들어:

- Worker Consumer가 `DISPATCHING -> PROCESSING` 전이를 수행하는 시점
- 복구 스케줄러가 같은 Job을 장기 체류로 판단하고 재복구를 시도하는 시점

이 두 흐름이 겹치면 상태가 꼬이거나 중복 복구가 발생할 수 있습니다.

이를 방지하기 위해 복구 로직 역시 일반 Consumer와 동일하게 **현재 상태를 조건으로 하는 원자적 update**를 사용하였습니다.

즉 복구 스케줄러도 “읽고 판단한 뒤 수정”하는 방식이 아니라, **특정 상태일 때만 전이 가능한 방식**으로 구현하였습니다.

</br>

#### 5. 서버 재시작 직후 즉시 복구 로직과 주기 스케줄러 간 중복 실행

시스템 재시작 후 복구 지연을 줄이기 위해 애플리케이션 시작 시점에 Outbox Publisher 및 장기 체류 복구 로직을 1회 즉시 실행하도록 설계하였습니다. 이후 동일 로직은 주기 스케줄러로도 동작합니다.

이때 startup 실행과 정기 스케줄 실행이 거의 동시에 수행되면,

- 동일 Outbox Event를 동시에 발행하려 하거나
- 동일 Job 복구를 동시에 수행하려 할 수 있습니다.

따라서 startup 시 즉시 실행되는 복구 로직과 정기 스케줄러 로직 모두 **멱등적으로 처리**했으며, 실제 처리 대상 선점은 DB 상태를 기반으로 원자적으로 수행하였습니다.

</br>

#### 6. terminal 상태 이후의 중복 처리 시도

이미 `SUCCEEDED` 또는 `FAILED`에 도달한 Job에 대해 늦게 도착한 메시지나 복구 로직이 다시 실행될 수 있습니다.

이 경우 완료 상태 이후에도 상태 전이가 허용되면, 이미 종료된 Job이 다시 `PROCESSING`으로 되돌아가거나 외부 Worker가 재호출될 수 있습니다.

이를 방지하기 위해 `SUCCEEDED`, `FAILED`는 **terminal 상태**로 정의하고,

terminal 상태 이후에는 추가 상태 전이를 허용하지 않도록 상태 전이 로직 레벨에서 제한하였습니다.

즉 Worker Consumer, Poll Consumer, 복구 스케줄러 모두 terminal state를 먼저 확인하고, 이미 종료된 Job은 처리 없이 종료하도록 설계하였습니다.

</br>

### 4.5 시스템의 처리 보장 모델
본 시스템의 처리 보장 모델은 At-least-once에 해당합니다. 이는 외부 Mock Workcer와 연동 시 메시지 브로커로 사용하게된 RabbitMQ의 메시지 전달 방식과 분산 시스템의 구조적 특성에 의해 결정되었다고 할 수 있습니다.

#### 1. 메시지 전달 보장

RabbitMQ는 기본적으로 **At-least-once delivery** 모델을 제공한다.

이는 다음과 같은 상황에서 동일 메시지가 다시 전달될 수 있음을 의미합니다.

- Consumer가 메시지를 처리한 뒤 ACK를 보내기 전에 장애 발생
- Worker 애플리케이션 중단 또는 재시작
- Consumer connection 종료

따라서 동일 Dispatch 또는 Poll 메시지가 여러 번 전달될 수 있으며, 시스템은 이를 정상적인 동작으로 간주하고 설계하였습니다.

</br>

#### 2. 외부 Mock Worker 호출의 특성

Dispatch 단계에서는 외부 Mock Worker에 이미지 처리 작업을 요청하게 됩니다.

이 호출은 외부 시스템에 실제 작업을 생성하는 **side effect**를 발생시킵니다.

만약 다음과 같은 상황이 발생하면 외부 작업이 중복 실행될 수 있습니다.

1. Worker가 Mock Worker 호출 성공
2. `PROCESSING` 상태 저장 전에 Worker 장애 발생
3. RabbitMQ가 동일 메시지를 다시 전달
4. 다른 Consumer가 Dispatch 로직을 다시 수행

이 경우 동일 Job에 대해 외부 작업이 두 번 생성될 가능성이 존재합니다.

외부 Mock Worker가 idempotency key 기반 멱등 처리를 제공하지 않는다면, 이러한 중복 실행 가능성을 완전히 제거하는 것은 어렵다고 판단했습니다.

</br>

#### 3. 시스템 전체의 처리 보장 모델

위와 같은 이유로 본 시스템은 **exactly-once 처리 보장을 제공하지 않습니다.**

대신 다음 전략을 통해 중복 실행 가능성을 최대한 줄일 수 있도록 설계하기 위해 노력했습니다.

- `PUBLISHED → DISPATCHING` 상태 선점을 통한 외부 작업 호출 단일화
- 메시지 ACK 지연을 통한 RabbitMQ redelivery 활용
- 상태 기반 멱등 처리
- terminal 상태(`SUCCEEDED`, `FAILED`) 이후 추가 상태 전이 차단
- Outbox 패턴을 통한 메시지 발행 정합성 보장
- 장기 체류 상태 감지를 통한 복구

이러한 전략을 통해 메시지가 여러 번 처리될 수 있는 환경에서도 **시스템의 최종 상태가 일관되게 유지될 수 있도록 설계하였습니다.**
